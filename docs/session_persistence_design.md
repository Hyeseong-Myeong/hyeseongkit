## 0. 목적과 범위

### 0-1. 목적
Bifrost로 **모델 라우팅**은 완성되었으나, **하나의 작업을 여러 모델/툴을 오가며 이어서 진행하는 것**은 불가능하다.
이 문서는 그 문제를 해결하는 **세션 영속화 계층**과, 그것을 담는 그릇인 **범용 CLI 허브 `hyeseongkit`** 을 설계한다.

## 1. 문제 정의

### 1-1. 근본 제약 — "전사"가 아니라 "상태"만 옮길 수 있다
모델의 내부 상태(KV 캐시, attention 컨텍스트)는 **원리적으로 이전 불가능**하다. 전사 전체 복사도 실패한다 — 로컬 8GB VRAM 모델의 짧은 컨텍스트, 유료 API의 선형 비용, 모델별 상이한 시스템 프롬프트.

**→ 옮길 수 있는 것은 증류된 상태(distilled state)뿐이다.** 이 문서 전체가 이 명제 위에 서 있다.

### 1-2. 다만 "증류"가 곧 "요약"은 아니다
증류를 요약과 동일시하면 **결정의 근거가 사라져 다른 툴에서 같은 논의를 반복**하게 된다.
→ 증류 = **버릴 것(서사·탐색 과정)은 버리고, 남길 것(결정·제약·식별자)은 원문 그대로 남기는 것**. 규약은 §7에서 정의한다.

### 1-3. ❗ v1 설계의 결함 (사용자 질문 ①에 대한 답)

**질문:** *"데스크톱의 세션 서비스가 유일한 라이터라는 말은, 맥북의 세션 영속화를 위해서는 맥북 → 옵시디언 → NAS 서버의 단계가 아니라는 말인가요?"*

**답: v1에서는 그렇습니다. 그리고 그것이 v1의 결함입니다.**

v1의 "단일 라이터" 규칙 하에서 맥북 작업을 저장하려면 이런 경로를 거쳐야 했다:

```
[v1 — 3홉 구조, 폐기]
맥북 Claude Code
   │ ① Tailscale HTTP
   ▼
데스크톱 세션 서비스 ──② 파일 쓰기──▶ 데스크톱 볼트
                                        │ ③ 데스크톱에서 Obsidian이 떠 있어야만
                                        ▼    LiveSync가 복제
                                    NAS CouchDB
                                        │ ④
                                        ▼
                                   맥북 볼트 (원래 출발지!)
```

세 가지 문제가 있었다:

| 문제 | 내용 |
|---|---|
| **불필요한 경유** | 맥북이 NAS에 직접 닿을 수 있는데 데스크톱을 우회한다 |
| **데스크톱 = 단일 장애점** | 데스크톱이 꺼져 있으면 맥북·휴대폰에서 **쓰기 전면 불가** |
| **Obsidian 의존** | LiveSync는 Obsidian 플러그인이므로, 데스크톱에서 **Obsidian이 실행 중이어야만** 복제된다. 헤드리스 서비스가 파일만 써 두면 아무 일도 일어나지 않는다 |

**v2의 답:** 허브를 **NAS로 옮긴다.** 모든 기기가 NAS 허브에 직접 쓴다. Obsidian은 쓰기 경로에서 빠지고 **읽기(열람) 경로**로만 남는다.

```
[v2 — 1홉 구조]
맥북 / 데스크톱 / (휴대폰)
   │ Tailscale HTTP (직접)
   ▼
NAS: hyeseongkit 허브 ──▶ CouchDB (SSOT)
                          │
                          └─▶ 마크다운 렌더 ──▶ livesync-bridge ──▶ 세션 전용 볼트 DB
                                                                      │
                                                    ┌─────────────────┼─────────────┐
                                                    ▼                 ▼             ▼
                                              데스크톱 Obsidian  맥북 Obsidian  휴대폰 Obsidian
                                                        (열람 전용)
```

## 2. 계층 모델 — hyeseongkit의 위치

### 2-1. 원본 4계층 → 이 시스템의 대응

| 영상 계층 | 영상 구현 | **이 시스템의 대응** | 채택 |
|---|---|---|---|
| **1. 영속 계층** | Bear + CLI + MCP | **Obsidian 볼트 + NAS CouchDB**<br>+ `hyeseongkit`의 CLI/MCP 접근 경로 | ✅ **기반으로 채택** |
| **2. 스킬 계층** | mingus-kit | **`hyeseongkit`** | ✅ **본 설계의 범위** |
| **3. 응용 계층** | mingus-studio (영상 제작) | 해당 없음 (콘텐츠 제작을 하지 않음) | ❌ 미채택 |
| **4. AI 연동 계층** | mingus-agent (Kotlin/Koog) | **Bifrost 게이트웨이 + LangGraph(`wiki_agent.py`)**<br>— 인프로세스 프레임워크 대신 **게이트웨이 형태로 이미 구현됨** | ◐ **이미 존재. 재구현하지 않음** |

**핵심:** `hyeseongkit`은 `mingus-kit`의 대응물이며, 그 첫 번째 기능은 원본과 동일하게 **세션 영속화**다.

### 2-2. 왜 2계층만 하는가
- **1계층(영속)** 은 이미 있다 — Obsidian + LiveSync + NAS CouchDB
- **4계층(AI 연동)** 도 이미 있다 — Bifrost가 모델 스위칭·폴백을 담당하고, `wiki_agent.py`가 LangGraph로 구조화된 파이프라인을 돌린다. 영상은 Kotlin/Koog로 JVM 안에서 푸는 문제를, 이 시스템은 **언어 중립적인 게이트웨이**로 이미 풀었다
- **3계층(응용)** 은 도메인이 다르다
- **비어 있는 것은 2계층뿐이다.** 그래서 여기만 만든다 — 원본의 철학("필요한 기능만 직접 설계") 그대로

### 2-3. 원본과 의도적으로 다르게 가는 지점 ⚠️

원본의 1계층은 **AI가 Bear를 CLI/MCP로 직접 읽고 쓴다.** 이 설계는 그렇게 하지 않는다.

| | 원본 (Bear) | 이 시스템 (Obsidian) |
|---|---|---|
| 저장소 사본 | 사실상 1개 (Bear 앱이 자체 동기화) | **4개** (데스크톱/맥북/휴대폰/CouchDB) |
| 쓰기 주체 | AI가 Bear CLI로 직접 | 여러 기기의 여러 툴이 동시에 |
| 충돌 처리 | Bear가 해결 | LiveSync **현재 설정상 수동 병합**(`resolveConflictsByNewerFile=false`) |
| 결론 | 파일 직접 접근으로 충분 | **직접 접근하면 충돌한다** → 허브 경유 (§3) |

**단, 철학은 유지한다.** "AI가 직접 읽고·쓰고·수정하고·검색한다"는 성질은 그대로다 — 다만 경로가 *파일시스템*이 아니라 *`hyeseongkit` CLI/MCP*일 뿐이다. AI 입장에서는 차이가 없다.

> `hyeseongkit`은 어떤 AI 서비스도 호출할 수 있는 **도구**이지, 스스로 판단하는 **에이전트**가 아니다.

## 3. 🔑 SSOT 확정 (사용자 질문 ③에 대한 답)

**질문:** *"볼트는 맥북·데스크톱에 모두 있고 NAS CouchDB로 영속화된다. 그럼 어디를 단일 진실 원천으로 두고, 어디에 접근하도록 할 것인가?"*

### 3-1. 문제의 정확한 성격
현재 "볼트"는 **4벌** 존재한다:

| 사본 | 위치 | 성격 |
|---|---|---|
| 데스크톱 볼트 | `<VAULT_PATH>` | 로컬 복제본 |
| 맥북 볼트 | 맥북 로컬 | 로컬 복제본 |
| 휴대폰 볼트 | 휴대폰 로컬 | 로컬 복제본 |
| **NAS CouchDB** | NAS | **모든 복제가 수렴하는 지점** |

CouchDB 복제 토폴로지에서 **수렴점은 항상 NAS**다. 로컬 볼트는 최종적 일관성(eventual consistency)을 갖는 **캐시**일 뿐이며, 최대 60초(현재 설정) 뒤처질 수 있다.
→ **"볼트가 SSOT"라는 v1의 문장은 애매했다.** 어느 볼트인지 특정되지 않았기 때문이다.

### 3-2. 선택지 비교

| | **A안: 볼트 파일 우선** | **B안: 허브 DB 우선 ★권장** | C안: 양방향 하이브리드 |
|---|---|---|---|
| SSOT | 마크다운 파일 (어느 사본?) | **NAS CouchDB의 `hyeseongkit` DB** | 둘 다 |
| 쓰기 경로 | 각 기기가 자기 볼트에 씀 | 모든 기기 → 허브 API | 양쪽 다 허용 |
| 볼트의 역할 | 원본 | **렌더된 열람 뷰(파생물)** | 원본이자 뷰 |
| 충돌 | ❌ 잦음. 현재 `resolveConflictsByNewerFile=false`라 **수동 병합** | ✅ 서버가 쓰기를 직렬화 → 충돌 없음 | ❌❌ 최악 |
| 데스크톱 꺼짐 | ⚠️ 기기별로 다름 | ✅ 무관 (NAS만 살아있으면 됨) | ⚠️ |
| 헤드리스 운용 | ❌ Obsidian 실행 필요 | ✅ `livesync-bridge`로 해결 | ❌ |
| Obsidian 전제 충족 | ◎ | ○ (열람·검색은 그대로 Obsidian) | ◎ |
| 구현 복잡도 | 중 | 중 | **높음** |

**A안의 개선형 — A′안 (파일 단위 이벤트 소싱) — 🚫 검토 후 기각 (2026-08-10)**

> **기각 사유:** 사용자 판단 — *"추후 마이그레이션은 번거롭다."*
> A′ → B 이전 비용이 낮다고 평가했으나, 실제로는 저장 백엔드뿐 아니라 **인증·프로젝트 식별·검색 경로가 함께 바뀌므로** 사실상 두 번 만드는 일이 된다.
> 아래 분석은 **기각된 대안의 근거 기록**으로 보존한다 (§7 N1 규약).

A안의 충돌 문제는 **"파일을 수정하지 않으면"** 사라진다.
각 `push`가 기기·시각별로 고유한 **새 파일**을 만들고(`sessions/events/E-<시각>-<기기>-<툴>.md`) 아무도 기존 파일을 건드리지 않으면, 서로 다른 파일이므로 LiveSync 충돌이 구조적으로 발생하지 않는다. `resume`은 이벤트 파일들을 읽어 상태를 조합한다.

| A′안 장점 | A′안 한계 |
|---|---|
| 인프라 추가 **0** (NAS 허브·별도 DB·bridge 전부 불필요) | ⚠️ **각 기기에서 Obsidian이 실행 중이어야 복제된다** — 터미널에서 `hk push`만 하고 Obsidian을 안 켜면 동기화가 일어나지 않는다 (조용한 실패) |
| 완전 오프라인 동작 (비행기에서도 push) | 휴대폰에서 쓰기 불가 |
| 원본(영상)의 방식에 가장 충실 | 규모가 커지면 검색이 파일 스캔 |
| **B안으로 이전이 쉬움** (이벤트 파일을 허브로 임포트) | `resume` 시 로컬 볼트가 최신이 아닐 수 있음 |

→ ~~A′안은 Phase 0/1의 저비용 출발점으로 적합하다.~~ **기각.** 처음부터 B안으로 간다.

### 3-3. ✅ 확정안 (D1 확정, 2026-08-10)

> **SSOT = NAS CouchDB의 `hyeseongkit_sessions` 데이터베이스.**
> **Obsidian 볼트 = 허브가 렌더한 열람 전용 뷰(파생물).**
> **모든 기계적 접근 = 반드시 허브 API를 경유한다. 볼트 파일을 직접 읽거나 쓰지 않는다.**

**이 결정의 파급:** NAS 허브가 **Phase 1의 전제**가 되었다. 따라서 **D3(NAS 사양 조사)가 착수를 막는 선행 항목으로 승격**된다 (§11).

**전제 2("영속화 기반은 Obsidian")와의 관계:**
이 전제는 **"내 작업 기록이 옵시디언에서 보이고, 검색되고, 링크되고, 휴대폰에서도 열린다"**로 충족된다.
쓰기 경로까지 Obsidian이어야 한다는 뜻은 아니며, 오히려 쓰기까지 Obsidian에 맡기면 §3-2의 충돌·헤드리스 문제로 **전제 자체가 무너진다.**
→ 다만 이는 전제의 재해석이므로 **사용자 확인 사항(§11 D1)** 으로 둔다.

### 3-4. 접근 규칙 (외워야 할 3줄)
1. **쓸 때:** 어떤 기기·어떤 툴이든 → `hyeseongkit` CLI/MCP → NAS 허브 API → CouchDB
2. **기계가 읽을 때:** 허브 API (`resume`, `search`) — **볼트 파일 접근 금지**
3. **사람이 읽을 때:** 아무 기기의 Obsidian (최대 60초 지연 감수)

### 3-5. 정합성 보장 규칙
| 규칙 | 내용 |
|---|---|
| 렌더 방향은 **단방향** | 허브 → 볼트. 볼트 → 허브 역류 없음 |
| 렌더 파일 헤더에 경고 삽입 | `> ⚠️ 이 파일은 hyeseongkit이 생성한 뷰입니다. 직접 수정해도 다음 렌더에서 덮어써집니다.` |
| 사람이 볼트에서 뭔가 추가하고 싶으면 | 별도 파일(`_notes.md`)에 쓰고, 허브가 이를 **읽기 전용 첨부**로 흡수 (§11 D6) |
| 허브 DB 손실 시 | 렌더된 마크다운으로 **재구성 가능**해야 함 → 렌더 파일에 이벤트 ID 포함 |

## 4. 아키텍처

### 4-1. 실행 위치 조언 (사용자 질문 ⑥에 대한 답)

**질문:** *"실행 위치는 NAS 혹은 데스크톱이 적절해 보이는데, 둘 중 더 적절한 곳은?"*

**답: NAS. 단 GPU/로컬 모델 작업은 데스크톱에 위임하는 분리 구조로.**

| 판단 기준 | NAS | 데스크톱 | 승자 |
|---|---|---|---|
| **항시 구동** | 24/7 가동이 존재 이유 | 워크스테이션. 끄고 켬 | **NAS** ★ 결정적 |
| **데이터 지역성** | CouchDB가 이미 여기 있음 | 네트워크 왕복 필요 | **NAS** |
| **필요 성능** | 세션 허브는 JSON 읽기/쓰기 + HTTP = **I/O 바운드**. 약한 CPU로 충분 | 과잉 | **NAS** |
| **기존 부하** | CouchDB 정도 | Ollama + Bifrost + ChromaDB + 봇 2개 + IDE. 이미 포화 | **NAS** |
| **GPU 필요 작업** | 불가 | RX 6600 XT | **데스크톱** |
| **소음/전력** | 이미 켜져 있음 | 세션 하나 때문에 24시간 켜둘 수 없음 | **NAS** |
| **배포 형태** | Docker 컨테이너 1개 추가 | 프로세스 추가 | 무승부 |

**결론적 근거:** 세션 영속화의 가치는 **가용성**에서 나온다. "이동 중에 이어서 하려 했는데 데스크톱이 꺼져 있어서 안 됨"이 한 번이라도 발생하면 이 시스템은 신뢰를 잃고 사용되지 않는다.

**분리 원칙:** (v2.5에서 "렌더"가 NAS로 복귀 — D4 (C) 확정, §4-1-3)
| 종류 | 위치 | 이유 |
|---|---|---|
| 상태 저장 / 조회 / 인증 | **NAS** | 항상 되어야 함 |
| **볼트 마크다운 렌더** | **NAS** (허브 렌더러 + livesync-bridge) | 세션 **전용** 볼트 DB에만 쓰므로 위키 볼트 위험 없음. 데스크톱 가동률과 무관하게 항상 최신 (§4-1-3) |
| 요약 생성 (LLM 호출) | 데스크톱 Bifrost 또는 클라우드 API | GPU/키 필요 |
| 의미 검색 (임베딩) | 데스크톱 ChromaDB | GPU 필요 |

> ⚠️ **핵심 설계 규칙: `push`는 LLM 없이도 반드시 성공해야 한다.**
> 데스크톱이 꺼져 있으면 요약·임베딩을 건너뛰고 **원문 이벤트만 저장**한 뒤, 나중에 지연 처리(deferred job)한다.
> LLM 호출을 쓰기 경로의 필수 단계로 두면 NAS로 옮긴 의미가 사라진다.

| **L1** | uvicorn **워커 1개**, 전 구간 **async I/O**. 블로킹 호출 금지 | ✅ 유지 | 여전히 2코어. 멀티워커는 컨텍스트 스위칭 손해 |
| **L2** | **NAS에서 LLM 호출·임베딩·요약을 하지 않는다** | ✅ 유지 | CPU가 아니라 **GPU·API 키가 없기 때문**. §4-1 분리 원칙 |
| **L3** | **폴링 금지.** 변경 감지는 CouchDB **`_changes`** 구독 | ✅ 유지 | 폴링은 상시 낭비. 설계 품질 문제 |
| **L4** | 컨테이너 **CPU 제한** | ⚠️ **수단 변경 (2026-08-12 실측)** | 목적(폭주가 CouchDB를 굶기지 않게)은 유효하나 **수단이 불가능했다.** Synology 커널에 CFS 쿼터가 없어 `cpus:`는 컨테이너 생성 자체가 거부된다(`NanoCPUs can not be set…`). **`cpu_shares: 512`(상대 가중치)로 대체** — 경합 시 CouchDB의 절반만 가져간다. **상한이 아니라 우선순위**이므로 "최대 1코어" 보장은 이 하드웨어에서 불가. 그만큼 **L7 관측의 비중이 커진다** |
| **L5** | 조회 결과 메모리 캐시 | 🔽 선택 | 필수 아님. 느려지면 도입 |
| ~~**L6**~~ | ~~추가 런타임 금지~~ | 🚫 **철회** | CPU 여유 확보로 근거 소멸. **D4를 뒤집었던 근거였음** |
| **L7** | 배포 후 **1주 CPU 관측**, 기준선 대비 이상 시 롤백 | ✅ 유지 | 좋은 배포 습관. **배포 전 기준선(현재 <10%) 기록 필수** |

### 4-1-3. ✅ 볼트 렌더 경로 (D4 확정)

> ✅ **확정 (2026-08-11): (C) 세션 전용 별도 볼트.**
> 사용자 판단 — 데스크톱을 며칠씩 켜지 않는 날이 많아, (B)의 최신성 약점(볼트 뷰가 데스크톱 가동률에 종속)이 실사용에서 치명적.
> 감수하기로 한 비용: ① 위키로 가는 `[[링크]]` 불가 ② 기기마다 볼트 2개 등록 ③ 브리지 유지보수(S2·S4).
> 아래 비교 분석과 기각 근거는 원문 보존한다 (§7 N1).

v2.3에서 렌더러를 데스크톱으로 옮긴 근거는 **두 가지**였다.

| 근거 | 현재 상태 |
|---|---|
| ① NAS CPU 여유 부족 (L6) | 🚫 **소멸** — 오류였고 정상화됨 |
| ② `livesync-bridge`가 **볼트 DB에 직접 쓴다** (R3) | ✅ **여전히 유효** — CPU와 무관한 위험 |

**→ "NAS에 둬도 되지 않나"는 질문은 타당하다. 근거 ①이 사라졌으므로 NAS 복귀가 가능하다.**
남은 판단은 **"볼트 DB 직접 쓰기 위험"과 "휴대폰 최신성" 사이의 교환**이다.

#### 선택지

| | **(A) NAS + livesync-bridge** | **(B) 데스크톱 hk 렌더러** | **(C) 세션 전용 별도 볼트** |
|---|---|---|---|
| 실행 위치 | NAS (Deno 컨테이너) | 데스크톱 (Python, `hk` 재사용) | NAS (Deno) + 전용 CouchDB DB |
| 볼트 뷰 갱신 조건 | **NAS만 켜져 있으면 됨** ✅ | 데스크톱 + Obsidian 실행 중일 때만 | **NAS만** ✅ |
| **휴대폰 최신성** | ✅ 항상 최신 | ❌ 데스크톱이 며칠 꺼져 있으면 그만큼 낡음 | ✅ 항상 최신 |
| 기존 위키 볼트 손상 위험 | ⚠️ 있음 (완화 가능) | ✅ 없음 (Obsidian 정상 경로) | ✅ **없음** (DB가 분리됨) |
| 위키 문서로 `[[링크]]` | ✅ 가능 | ✅ 가능 | ❌ **불가** (볼트 간 링크 안 됨) |
| 기존 볼트 파일 수 증가 | 있음 (R6) | 있음 | ✅ 없음 |
| 기기별 추가 설정 | 없음 | 없음 | ⚠️ 기기마다 볼트 2개 등록 |
| 핸드오프 영향 | 없음 | 없음 | 없음 |

#### 위험의 실체 — LiveSync는 마크다운을 파일로 저장하지 않는다

(A)와 (C)의 위험을 정확히 이해하려면 LiveSync의 저장 방식을 알아야 한다.

```
"sessions/T-xxx.md" 라는 파일을 볼트 DB에 넣는다는 것은…
  ├── 엔트리 문서  : 경로, mtime, 크기, 청크 ID 목록
  └── 청크 문서 N개 : 내용 조각 (중복 제거됨, 다른 파일과 공유될 수 있음)
```

즉 **일반 파일 쓰기가 아니라 플러그인 내부 포맷으로 문서를 조립해 넣는 것**이다. 여기서 실수하면:

| 실패 모드 | 결과 |
|---|---|
| 엔트리/청크 불일치 | 해당 파일이 깨진 채로 **3기기 전체에 복제** |
| 청크는 공유 자원 | 잘못 건드리면 **다른 파일까지** 영향 가능 |
| 플러그인 tweak 협상 | 실측 로그에서 LiveSync가 tweak 변경 시 *"Database closed for reset"* 을 수행하는 것이 확인됨. 브리지가 이 협상에 어떻게 반응하는지 **미검증** |
| 버전 드리프트 | LiveSync 업그레이드 시 포맷이 바뀌면 브리지도 따라가야 함 (**지속적 유지보수 부담**) |

**이 위험은 CPU와 무관하며, 안전장치로 낮출 수는 있어도 0으로 만들 수는 없다.**

#### 판단 — (A)는 (C)에 지배당한다

핵심은 **"어느 DB에 쓰느냐"** 다. (A)와 (C)는 브리지를 쓴다는 점에서 같고, **대상 DB만 다르다.**

| | (A) 기존 볼트 DB에 쓰기 | (C) 세션 전용 DB에 쓰기 |
|---|---|---|
| 최악의 경우 피해 | **누적된 위키 지식 손상** — 재생성 불가 | **세션 뷰만 손상** — SSOT에서 **전량 재생성 가능** (§3-3) |
| 휴대폰 최신성 | ✅ 동일 | ✅ 동일 |
| 유지보수 부담 | 동일 | 동일 |

> **(C)는 (A)와 같은 이점을 주면서 피해 범위만 없앤다.** 유일한 차이는 **위키로 가는 `[[링크]]`가 끊긴다**는 것.
> → **(A)를 고를 이유는 "링크가 반드시 필요하다"는 경우뿐이다.**

#### 실질적 선택은 (B) vs (C)

| 질문 | 답이 "예"라면 |
|---|---|
| **데스크톱을 거의 매일 켜는가?** | **(B)** — 뷰가 하루 이상 낡을 일이 없다. 가장 단순하고 위험 0이며 링크도 유지된다 |
| 며칠씩 안 켜는 날이 많은가? | **(C)** — 최신성을 얻고, 링크 단절과 기기당 볼트 2개 설정을 감수한다 |

**피해의 비대칭성:** (B)의 실패는 *"휴대폰 뷰가 하루 낡음"* — 되돌릴 수 있고 파괴적이지 않다. (A)의 실패는 *"누적 지식 손상"* — 비대칭이 크다. 확신이 없다면 **(B)에서 시작**하는 것이 합리적이다.

**(B)의 약점은 보완 가능하다:** 허브는 NAS에 있으므로, 데스크톱이 꺼져 있어도 휴대폰에서 **iOS 단축어로 허브 API를 직접 조회**하면 최신 상태를 볼 수 있다 (D23). 단축어는 HTTP POST + 토큰이면 되므로 만들기 쉽다.
→ **(B) + D23 조합이면 (B)의 유일한 단점이 사실상 해소된다.**

#### (A) 또는 (C) 선택 시 필수 안전장치

| # | 조치 |
|---|---|
| **S1** | 도입 전 **볼트 전체 백업** (파일 + CouchDB 덤프 양쪽) |
| **S2** | **테스트용 별도 CouchDB DB**에서 먼저 검증. 실제 DB 연결은 검증 통과 후 |
| **S3** | `baseDir`로 **`sessions/`만** 브리지 범위에 노출 |
| **S4** | LiveSync **플러그인 업그레이드 전 반드시 브리지 호환성 확인** (버전 드리프트) |

> ⚠️ **(B) 선택 시:** 렌더러는 반드시 **한 기기에서만** 실행한다. 데스크톱·맥북 양쪽에서 돌리면 같은 파일을 써서 LiveSync 충돌이 난다. `project.toml`의 `renderer_device`로 지정.

> 📌 **어느 안을 골라도 SSOT는 바뀌지 않는다.** 볼트 뷰는 파생물이므로, 나중에 (B)↔(C) 전환은 **렌더 출력 위치만 바꾸는 일**이다. 데이터 마이그레이션이 아니다.

### 4-4. livesync-bridge — 검증 결과

> **상태: 채택 확정 (D4 (C), 2026-08-11).** 대상은 **세션 전용 DB `hyeseongkit_vault`** — 기존 위키 볼트 DB(`obsidian_vault`)에는 연결하지 않는다.
> **철회 조건:** LiveSync 버전 업그레이드 때마다 포맷 불일치로 유지보수 부담이 커지면 (B) 데스크톱 렌더러로 후퇴.

검증 결과 (2026-08-10 확인)
- Self-hosted LiveSync 개발자(vrtmrz)가 만든 **공식 계열 도구**. LiveSync 원격 볼트 ↔ 스토리지 간 커스텀 복제기
- **Obsidian 실행 불필요** — 헤드리스 서버 워크플로우가 본래 목적
- Deno 기반, **Docker Compose 지원**, `dat/config.json`으로 피어 설정
- 볼트별 개별 암호 구문(passphrase) 지원 → §11 D8(E2E 암호화)을 켜도 대응 가능
- `baseDir`로 **특정 폴더만 선택 동기화** 가능 → `sessions/`만 브리지에 노출 가능
- 기본적으로 `.obsidian/` 등 내부 파일 제외

> ⚠️ 이 도구는 볼트 DB에 **쓰기**를 한다. 도입 전 **볼트 전체 백업**과 별도 테스트 DB 검증을 반드시 선행할 것. (§12 R3)

### 6-2. 저장 구조 — 이벤트 소싱 (append-only) — D5 확정

**모든 `push`는 새 문서를 만든다. 기존 문서를 수정하지 않는다.**

```
CouchDB: hyeseongkit_sessions
├── evt:<thread>:<ts>:push      ← 불변. 원문 그대로
├── evt:<thread>:<ts>:decide    ← 불변
├── evt:<thread>:<ts>:close     ← 불변
└── view:<thread>               ← 재생성 가능한 materialized view (요약 포함)
```

| 이점 | 설명 |
|---|---|
| **충돌 원천 소멸** | 아무도 같은 문서를 수정하지 않으므로 CouchDB 충돌이 발생하지 않는다 |
| **요약 재생성 가능** | 요약 품질이 불만이면 원문 이벤트에서 다시 만들면 된다 |
| **감사 가능** | "그 결정 언제 어느 툴에서 했지?"에 답할 수 있다 |
| **§7 규약의 물리적 보장** | 원문이 물리적으로 삭제되지 않으므로 "요약 금지"가 규약이 아닌 **구조**로 강제된다 |

**Thread(스레드)** = 하나의 작업 단위. 툴을 바꿔도 유지된다. 여러 push 이벤트가 하나의 thread에 묶인다.

#### 6-2-1. 저장 모드 옵션화 (D5 후속)

기본은 `event`이되, 저장 계층을 **인터페이스로 분리**해 추후 다른 모드를 선택할 수 있게 한다.

| 모드 | 동작 | 용도 |
|---|---|---|
| **`event`** (기본) | push마다 불변 문서 추가. 상태는 fold로 계산 | 감사·복원·요약 재생성 필요 시 |
| `document` | thread 문서 1개를 갱신 | 저장량을 줄이고 싶을 때 |

설정 위치: 전역 기본값 + `.hyeseongkit/project.toml`의 `store_mode` (프로젝트별 재정의)

> ⚠️ **전환의 비대칭성:** `event` → `document`는 fold 결과를 쓰면 되므로 **무손실**이다. 반대(`document` → `event`)는 과거 이력이 없으므로 **복원 불가**다.
> → 그래서 **기본값을 `event`로 두는 것이 안전한 선택**이다. 나중에 줄일 수는 있어도 늘릴 수는 없다.
>
> ⚠️ **K0 유의:** 두 번째 모드를 **지금 구현하지 않는다.** Phase 1에서는 인터페이스만 분리하고 `event` 하나만 만든다. `document` 모드는 실제로 용량 문제가 관측된 뒤에 추가한다 (§12 R16).

### 6-5. 컨텍스트 예산 — 계층 반환

로컬 8GB VRAM 모델은 컨텍스트가 짧다. `resume`은 예산에 맞춰 **계층적으로 절단**한다.

| 계층 | 내용 | 대략 |
|---|---|---|
| **L0 (항상)** | frontmatter + `## 3. 할 일` + `## 4. 알아야 할 것` | ~600 토큰 |
| **L1** | `## 1. 컨텍스트` + `## 2. 한 일` 요약 + `## 5. 미결 질문` | ~1,200 토큰 |
| **L2** | 관련 이벤트 원문·링크 (요청 시에만) | 가변 |

> **L0는 절대 잘리지 않는다.** 예산이 모자라면 L1을 더 줄일 뿐이다. "다음에 뭘 할지"와 "알아야 할 함정"이 사라지면 핸드오프 자체가 무의미하기 때문이다.

| **섹션 분리** | `## 4. 알아야 할 것`은 요약 파이프라인에 **입력 자체를 하지 않음** |
| **길이 무제한 예외** | `## 4`는 토큰 예산 계산에서 L0로 분류되어 절단 대상이 아님 (§6-5) |

## 8. 확장성 — 스킬 플러그인 구조 (사용자 질문 ⑦에 대한 답)

### 8-1. 구조
```
hyeseongkit/
├── core/
│   ├── config      # 프로젝트/전역 설정
│   ├── transport   # 허브 HTTP 클라이언트, 재시도, 오프라인 큐
│   ├── auth        # 토큰 관리
│   ├── redact      # 마스킹 (모든 스킬이 공유·필수 경유)
│   ├── store       # CouchDB 이벤트 저장소
│   ├── render      # 마크다운 렌더 → 볼트
│   └── registry    # 스킬 등록/디스커버리
└── skills/
    ├── session/    ★ 이번 범위 — 원본 mingus-kit의 1번 기능
    ├── api/        외부 API 통합 — 원본 mingus-kit의 2번 기능
    │               (캘린더·시트·GA 등 → 데이터 분석·자동 리포팅)
    ├── wiki/       기존 ChromaDB 검색 흡수 (Phase 6)
    ├── review/     적대적 검증 파이프라인 (로드맵 4-3)
    ├── interview/  모의면접 + SM-2 (로드맵 4-2)
    ├── jd/         JD 매칭 (로드맵 4-4)
    └── portfolio/  포트폴리오 생성 (로드맵 4-1)
```

> 원본 `mingus-kit`의 두 핵심 기능이 **세션 영속화 + 외부 API 통합**이라는 점은, 스킬 계층이 "AI 관련 기능"만 담는 곳이 아니라 **내 업무 능력 전반을 담는 곳**임을 보여준다. `api` 스킬은 K0에 따라 **실제로 반복하는 수작업이 생겼을 때** 추가한다.

### 8-2. 스킬 계약 (인터페이스)
새 스킬이 구현해야 하는 최소 규격:

| 항목 | 내용 |
|---|---|
| `manifest` | 이름, 버전, 명령어 목록, 필요 권한, 민감도 기본값 |
| `commands` | CLI 서브커맨드 정의 (자동으로 MCP 도구 + HTTP 라우트로 노출됨) |
| `schema` | 입출력 Pydantic 모델 |
| `render()` | (선택) 볼트에 어떻게 보여줄지 |
| `on_event()` | (선택) 다른 스킬의 이벤트 구독 |

**한 번 구현하면 CLI·MCP·HTTP 세 표면에 동시에 노출된다** (K3). 새 AI 서비스가 나와도 어댑터만 추가하면 모든 스킬을 그대로 쓴다.

### 8-3. 스킬 간 연계 예시 (미래)
```
session.close  ──이벤트──▶  wiki.compile      (완료된 작업을 위키 문서로 승격)
session.push   ──이벤트──▶  interview.card    (막혔던 지점을 복습 카드로)
review.finding ──이벤트──▶  session.decide    (검증 결과를 결정 로그로)
```
> 단, 이는 **Layer 2 내부의 이벤트 연계**이며 자율 에이전트(Layer 3)가 아니다. 트리거는 규칙 기반이고 결과는 사람이 확인한다.

### 9-1. Claude Code 훅 설계
| 훅 | 동작 | 실패 시 |
|---|---|---|
| `SessionStart` | `hk resume --last --format packet` → 패킷 자동 주입 | **조용히 스킵** (세션 시작을 막지 않음) |
| `PreCompact` | `hk checkpoint --reason precompact` — 컴팩트 직전에 git 상태·전사 경로를 고정 | 경고 로그 |
| `SessionEnd` | `hk checkpoint --reason session-end` | 로컬 큐 적재 후 다음 실행 때 재전송 |

> **v2.8 정정 (설계서 §9-2 구체화, 사용자 승인 2026-08-11):** 훅은 셸 명령이라 세션 **본문**(AI가 작성 — D21)을 만들 수 없다. 따라서 훅의 저장은 **checkpoint(메타데이터 이벤트)**이고, 본문 있는 push는 `/hk:push` 또는 모델의 `hk_push` 호출로 한다. `Stop` 훅은 매 응답마다 실행되어 과도하므로 쓰지 않는다.

> ⚠️ **훅은 절대 blocking 하지 않는다.** 타임아웃 3초. NAS가 죽어도 Claude Code는 정상 시작해야 한다.

| **데스크톱이 꺼진 상태에서 맥북 push 성공률** | **100%** ← v2의 핵심 지표 |
| 요약에 의한 식별자 변조 | **0건** (§7-3 검증기) |
| 세션 데이터 시크릿 유출 | **0건** |
| 새 프로젝트에서 `hk init` → 첫 push까지 | 3분 이내 |
| "아까 뭐 하고 있었지?"를 다시 설명하는 횟수 | 주 1회 이하 |
